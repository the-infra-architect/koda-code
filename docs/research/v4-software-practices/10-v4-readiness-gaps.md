# V4 Readiness / Remaining Research Gaps

## Ready enough to shape V4

- quality-attribute profiling rather than a simplicity score;
- existing-project ecosystem detection before tool addition;
- adaptive quality contracts built from capabilities;
- risk-based testing;
- threat-surface security;
- deterministic validation of AI output;
- measured performance/resource reasoning;
- topology-aware storage selection;
- explicit network-filesystem safeguards;
- local quality gates without mandatory hosted CI;
- optional/platform-aware Sonar/GitHub security integration;
- monorepo native graph reuse;
- accessibility as a real UI quality dimension;
- product-language clarification for beginners;
- expert technical constraints treated as requirements.

## Not ready as universal hard policy

- complexity thresholds;
- coverage percentages;
- dependency “health” scores;
- fixed greenfield stack mappings;
- universal DB;
- Docker-by-default;
- universal observability stack;
- automated license/legal decisions;
- universal DB migration strategy;
- Koda-vs-raw-agent superiority claims.

## Post-research product questions that need real usage evidence later

- Which languages/stacks should receive first-class generated setup in V4 vs only detection?
- Which specialist routing decisions produce value vs extra model calls?
- Which quality checks are too slow/noisy for interactive Koda use?
- How often beginners are actually blocked by product-language clarification.
- Whether extension packaging should bundle the Python engine.
- How Koda compares against raw Copilot once live model access is available.
